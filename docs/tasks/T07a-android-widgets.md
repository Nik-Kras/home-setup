# T07a: Android home-screen widgets (M3)

Implementer: Codex (Sol 6.2, effort high) via /codex:rescue, in a worktree the orchestrator creates (branch `t07a`, changes left uncommitted because Codex's sandbox cannot write git state; the orchestrator commits). Reviewer: Fable 5.2. iOS widgets are a separate later task (T07b) and reuse your data contract.

## Goal
Small, medium and large Android widgets that show the shared list live, match `design-ref/screens/WidgetsAndroid.png` (private local image, read it with the Read tool from the main checkout path given in docs/tasks/README.md), open the right screen of the app on tap, and let the user mark an item as got straight from the large widget without opening the app.

## Library choice (already researched, do not re-research)
`react-native-android-widget` 0.26.0 (config plugin, JS-defined widgets rendered by FlexWidget, TextWidget, ListWidget, SvgWidget; click actions `OPEN_APP`, `OPEN_URI`, or a custom action that runs a headless JS `widgetTaskHandler`; `requestWidgetUpdate`; plugin option `widgets[]` and `fonts`). Docs: https://saleksovski.github.io/react-native-android-widget/ . Verify against the installed version's README before coding. Install with `npx expo install react-native-android-widget` (if it is not in Expo's known versions use the version above and say so). The Expo SDK is 58 and the architecture is the new one: confirm compatibility from the package notes. Do NOT install or enable `expo-widgets` Android.

## Do
1. Pure data builder `app/src/domain/widgetData.ts` with unit tests (this is the contract iOS will reuse): `buildWidgetData(items, tasks, me, now)` returns `{ v: 1, updatedAt, leftCount, urgentCount, nextUp: {id,name,room?,urgent}|null, top: [{id,name,status,urgent,icon}] (3 items, urgent first), rooms: [{room, items:[{id,name,status,urgent}]}] (max 4 rows total for the large widget, grouped, only items still left), tasksDue: {todayCount, next: {id,title,daysLeft}|null} }`. Icon is a key from the existing glyph names. Status labels are the app's words (Needed, Looking, Ordered, Delivered, Installed). No personal data beyond item names and first names that are already in the store.
2. Three widgets registered in the plugin config in `app.json` (names `OurFlatSmall` 2x2, `OurFlatMedium` 4x2, `OurFlatLarge` 4x4; resizeMode, previewImage generated or omitted, `updatePeriodMillis` 1800000) using the design's look: dark surface `#171B19` with a 1px hairline, serif numbers, mint add button 44dp, neutral status chips (Ordered amber tint, Delivered mint tint), coral "!" for urgent, owner as nothing (no avatars needed). Fonts: Instrument Serif and Geist if the plugin's `fonts` option supports them (the packages `@expo-google-fonts/*` hold the ttf files); fall back to the system font and say so.
   - Small: "Our flat", big count of items left, "to get", mint plus button.
   - Medium: header "Our flat · n left" with plus button, top 3 rows (glyph tile, name, status chip).
   - Large: header, rooms with up to 4 rows total, each row has a check circle (tap marks it got) and the status chip, plus "Updated just now" style small text (age from `updatedAt`, 13px minimum).
3. Taps: plus button `OPEN_URI` `homesetup://add-item` (opens the app on the Buy tab with the add input focused: add the deep link route handling in the app, e.g. a query param or route `src/app/add-item.tsx` that redirects to `/` and focuses the input via a store flag; keep it minimal and tested where pure), row body `OPEN_URI homesetup://item/<id>`, widget background `OPEN_APP`, check circle custom action `MARK_GOT` handled headless.
4. Headless handler `widgetTaskHandler` registered from the app entry. `main` in `app/package.json` currently points at `expo-router/entry`; follow the library's register-task-handler docs: create `app/index.ts` that registers the handler and then imports `expo-router/entry`, and point `main` at it. For `MARK_GOT` the handler must: load the stored snapshot, apply `markGot` (domain) to the item, write the change through the SAME offline queue the app uses (field-level patch `status`/`delivered_at` via `diffToOps`, see `app/src/data`), persist the new widget data and call `requestWidgetUpdate`. If the app and the handler could race on the queue storage, make the append safe (read-modify-write with a simple in-process lock plus re-read) and say how.
5. Data flow: the app computes `buildWidgetData` after every store change (debounced 500 ms) and after realtime refreshes, stores the JSON in AsyncStorage under a documented key, and calls `requestWidgetUpdate` for the three widgets. Put this in a small module `app/src/data/widgetSync.ts` called from the store provider with minimal edits to `store.tsx`.
6. Demo mode and signed-out state: widgets show "Open the app to sign in" instead of crashing.
