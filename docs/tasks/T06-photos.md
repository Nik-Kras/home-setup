# T06: Photos (M2)

Implementer: Codex (Sol 6.2, effort high) via /codex:rescue, in a worktree the orchestrator creates. Reviewer: Fable 5.2. Depends on the merged detail screens (T02 to T05).

## Goal
Take or pick a photo for an item (and for a task area step later), upload it to the private Supabase bucket `photos`, show it in the item detail and on the Home screen (photo replaces the glyph tile), and keep working offline: a photo added without network is kept on the device and uploaded when the connection returns.

## Do
1. Dependencies (use `npx expo install`, fetch SDK 58 docs first): `expo-image-picker` (camera and library, permissions through its config plugin in `app.json`, with plain-language permission strings that mention no personal data) and `expo-image-manipulator` (resize to at most 1600 px on the long edge, JPEG about 0.7 quality, target under 300 KB). Say exactly which packages you added; the orchestrator rebuilds the native app.
2. Pure logic in `app/src/domain/photos.ts` with tests: storage path `items/<itemId>/<uuid>.jpg`, size checks, the pending-upload state machine (pending, uploading, done, failed with retry count), and picking the cover photo (the newest) for an item.
3. Data layer: a `PhotoQueue` beside the existing `OpQueue` (reuse its persistence and flush pattern; own storage key). Steps for one photo: save the processed file to the app's document directory, enqueue; on flush upload to the `photos` bucket (supabase storage upload with the file bytes, `contentType: image/jpeg`, never `upsert`), then insert the `item_photos` row (id generated on the device, so a retried insert is idempotent: upsert with `ignoreDuplicates`). A failed upload retries on the next flush; a permanent refusal (4xx) is dropped with a logged warning and the photo shows a "failed" state the user can retry or delete.
4. Reading: load `item_photos` with the items (extend `loadAll`, graceful when the table is empty), create signed URLs (`createSignedUrls`, 1 hour) in one batch, cache them in memory, refresh on expiry. Show the local file immediately for photos still pending.
5. UI: item detail gets a photo row (design: `design-ref/screens/Item.png`, "Add photo" dashed tile 92x92 with camera icon, then thumbnails; tap a thumbnail for a full screen viewer with a Delete action for the two people, built with RN `Modal`). A small "Add photo" sheet offers Camera or Library. The Home screen photo cards (design: `design-ref/screens/Home.png`) show the newest photo for items that have one, keeping the opaque dark scrim behind the serif caption so text stays readable; items without a photo keep the glyph tile.
6. Deleting: the two people can delete (storage delete policy exists for people only; Claude cannot). Delete removes the `item_photos` row and the file; if offline it is queued.
7. Accessibility: labels on every control, 44dp targets, photo thumbnails have `accessibilityLabel` "Photo of <item name>, <n> of <m>".

## Acceptance criteria
- `npm test`, `npx tsc --noEmit`, `npx expo export --platform android` pass; photo pure logic and the queue (offline, retry, drop, restart persistence) are unit tested with fakes.
- Nothing in the repo contains secrets or real photos; test fixtures are generated bytes.
- A photo taken with no network is shown at once, survives an app restart and uploads when online.
- Upload never overwrites an existing file (unique names); retried inserts never duplicate.
- Claude's account can add photos but cannot delete them (enforced by the database; do not work around it).
